## 抓取代理的三步，哪一步最容易白干

**第一步，抓取。** 免费代理站的结构都简单，翻页参数加 xpath 取表格前两列就能拼出 `ip:port`。真正的坑在编码和反爬：不少站点是 GBK 页面，直接 `response.text` 拿到的是乱码，得先 `encode('ISO-8859-1')` 再 `decode('gbk')`；另外对方会封你的抓取 IP、会改 DOM 结构，你的解析规则要跟着改。

**第二步，验证。这是决定池子质量的一步，也是多数教程糊弄过去的一步。**

常见的写法是：拿代理去请求百度，`timeout=1`，状态码 200 就算可用。这套写法能跑通 demo，但有三个硬伤：

1. `timeout=1` 会误杀。跨境线路、住宅出口响应两秒很正常，你把它当坏的扔了。
2. 只测百度说明不了任何问题。你要抓的站可能有自己的 WAF、自己的区域限制，百度通不代表目标站通。
3. 没有失败计数。一个 IP 今天能通、明天不通，脚本不知道，池子里一直留着。

更可靠的做法是两段式验证。先拿代理去请求 httpbin 这类回显服务，从返回内容里判断三件事：出口 IP 是不是真的变了（代理生效）、是否支持 HTTPS、匿名度属于哪一档（高匿 / 匿名 / 透明，透明代理会在头里带出你的真实 IP，等于没用）。过了这一关的，再拿去访问你真正的目标站，在合理时间内拿到正确内容才算数。一个目标站配一套验证脚本，别指望一个脚本通吃所有站。

**第三步，入池。** 这一步的细节放在下面单独讲。

## 池子怎么管：五个状态、60 秒提前量、让爬虫自己上报坏 IP

代理池的本质是状态管理。给每个 IP 一个状态，比维护一个大列表有用得多：

| 状态 | 含义 |
| --- | --- |
| available | 当前可用，可分配 |
| using | 正在被任务占用 |
| abnormal | 连接异常，暂时隔离 |
| expiring | 即将过期，不再分配新任务 |
| expired | 已过期，清理 |

过期判断直接用接口返回的 `expire_at_timestamp` 和 `time.time()` 比。生产环境还要留提前量，比如**距离过期不足 60 秒就不再分配给新任务**，否则任务刚拿到 IP 它就过期了。

存储按规模选，三种方案对应三种场景，没有哪个是标准答案：单机跑用 Python 内存列表就够；多进程或多机共享用 Redis，按 `proxy:available`、`proxy:using`、`proxy:abnormal` 分键；早几年的项目用 MySQL 或 SSDB，能跑，但过期清理和并发查询要自己扛。

对外接口准备三个就够：`get` 拿一个、`delete` 删一个、`refresh` 触发补充。这里有个比定时检测更靠谱的设计：**让爬虫自己上报坏 IP**。爬虫在真实目标站上遇到 403、超时、返回异常页，直接调 `delete` 把 IP 踢掉。定时检测程序永远模拟不出你所有目标站的真实情况，而爬虫每天都在上面跑。定时任务作为兜底，默认 20 分钟全量刷新一次是常见的配置，检测本身很慢，要用多线程或异步跑。

请求侧还有几个细节：`timeout=(5, 15)` 比单一超时值合理；分别捕获 `requests.Timeout`、`requests.ConnectionError`、`requests.RequestException`；重试次数设上限，连续异常的 IP 直接移出可用池。

## 付费代理 API 长什么样

如果你打算走按量提取这条路，接口形态基本是固定的：先用用户名密码换一个 Token，再调提取接口，参数里有数量、协议（HTTP 或 SOCKS5）、有效期、省份、城市、去重天数、返回格式。返回的 JSON 里带 `ip`、`http_port`、`s5_port`、`expire_at_timestamp`，还有地区、城市、运营商字段。

两个容易踩的点：

- **频率限制。** 单个账号每秒 30 次提取请求是常见的量级，超了会被拒。批量提取、缓存 Token、池内复用，能把调用量压下来。
- **错误要分类。** 返回"余额不足"和"可用线路资源不足"是两回事，一个是钱，一个是当时没货。都不该当成网络异常去重试。

## 什么时候该停止自建

给几条可量化的判断线，中两条以上，自建就不划算了：

- 每天花在改解析规则、补池子、修验证脚本上的时间超过半小时，而且还在涨；
- 目标站超过 3 到 5 个，每个都要单独写一套验证脚本；
- 并发要从几十提到几百，需要多机共享池子，得上 Redis 做分布式；
- 免费 IP 的匿名度和纯净度不够，目标站已经按账号、Cookie、设备特征做识别了。

第三条值得单独说。GitHub 上一个用 Scrapy 抓免费代理并验证的开源工具，从 2017 年更新到 2020 年，多数据库支持、分布式部署、多进程验证这几项还挂在 TODO 里没动。这类工具的结局很典型：能跑，能给你一个池子，但停在"个人够用"的水平，往生产走的那一步没人替你走完。你自己接着写，写的就是同一件事。

另一条路是把出口外包出去。要么买按量提取的代理 API，接受它需要自己验证、有频率限制、错误要分类；要么买一台住宅 IP 机器，接受它固定、不轮换、端口受限。两条路省下的都是同一件东西：每天那半小时。

## 常见问题

**免费代理为什么刚测通就失效？**
你测通的那一刻，它只是当时能连。免费 IP 是公开资源，同一时间可能被几百人拿去打同一个站，目标站一封就是一片；网站下线、运营商回收地址也会让它随时消失。池子里必须有过期时间和失败计数，否则你永远在用昨天的数据做今天的判断。

**抓取代理这件事本身会被封吗？**
会。免费代理站会封你的抓取 IP，也会改版让你的解析规则失效，所以抓取端要有 UA 伪装、要有失败告警。另外，代理只改变出口，不改变你的请求行为，目标站照样能按频率、账号、Cookie 识别你，请求速率还是得自己控。

**池子要多少 IP 才够？**
取决于目标站的限流阈值和你的并发，不是越多越好。IP 数量增加不代表能无限提高并发，目标站的访问规则和对方服务器的承载能力才是上限。先小规模测出单 IP 的安全频率，再乘出需要的数量。

**HTTP 和 SOCKS5 怎么选？**
`requests` 原生支持 HTTP 代理，用 SOCKS5 要额外装 `requests[socks]`。有些工具链或目标环境只支持其中一种，选之前先看你自己的栈，别买完才发现接不上。

**SixtyNet 能当代理池 API 用吗？**
不能。它是一台固定 IP 的 VPS，没有提取接口、没有地区筛选、IP 不轮换。它适合做池子里的长期固定节点，不适合做需要海量轮换 IP 的采集。
